## What this project is

A Next.js landing page for a network of livestreamers. One codebase serves
**13 streamers** (and growing) from one `data/streamers.ts` config — not
separate projects per streamer. Deployed to Cloudflare Workers via OpenNext,
live at real custom domains (not just `workers.dev`):

- `*.liveth.net` and `*.liveth.org` (wildcard, subdomain-per-streamer via
  `middleware.ts`), e.g. `enjoy.liveth.net`, `holden.liveth.net`.
- Worker name: `nexplay-streamers`.

Run everything from this directory:

```text
/Users/fan/Documents/Codex/2026-07-27/nexplay-enjoy-live-landing-page-stack/nexplay-app
```

## Stack

Next.js 15 App Router, React 19, TypeScript, Framer Motion, GSAP, Lucide
Icons + react-icons, OpenNext for Cloudflare, Wrangler, Cloudflare Workers.
No Tailwind in active use — styling is one large hand-written
`app/globals.css` (11,000+ lines — see the CSS warning below, it's the
single biggest trap in this repo).

## Commands

```bash
npx tsc --noEmit -p .        # typecheck — run before every build
npm run build                 # next build — run before every deploy
npm run deploy                 # opennextjs-cloudflare build + deploy
```

**Known gotcha:** `npm run deploy` may fail with
`Next.js version X is not supported by the Next.js team` — this is
`@opennextjs/cloudflare`'s version allowlist being stale, not an actual
incompatibility. Work around it without downgrading Next.js:

```bash
npx opennextjs-cloudflare build --dangerouslyUseUnsupportedNextVersion
npx opennextjs-cloudflare deploy
```

**After every deploy**, open the live URL in a **fresh browser tab** before
concluding anything is broken — the very first load right after a deploy
sometimes 404s a stale chunk or shows a transient `ChunkLoadError` while
Cloudflare's edge finishes propagating. Reload once before treating it as a
real bug.

## ⚠️ CSS architecture — read this before touching `app/globals.css`

This file has **duplicate rules for the same selector at different
line numbers** — not always inside `@media` blocks, sometimes just plain
re-declarations added during earlier iteration (e.g. `.social-item`,
`.brand-text`, `.section-heading h2` each have 4–9 separate base
definitions scattered through the file). The **last one in source order
wins at equal specificity**, and it is genuinely hard to know which one
that is just by reading.

**This has caused real, deployed bugs multiple times**: a streamer's brand
name rendering invisible (wrong color inherited from an unrelated
duplicate), social cards staying white when they should be dark, etc.

**The reliable fix pattern, used throughout this file**: when you need a
style to apply to one streamer (or one streamer in one mode) and nothing
else, **don't try to find and edit the "right" existing rule** — add a
**new rule with higher specificity** instead, so it wins regardless of
which duplicate is technically last:

```css
/* generic/base rule wins for everyone else, no matter where it lives */
.app-shell[data-streamer="X"] .some-class {
  /* ... */
}
```

An attribute selector (`[data-streamer="X"]`) beats a bare class every
time, so this is safe to append anywhere, including at the very end of the
file. When in doubt, **verify the actual computed style in a real browser**
(`getComputedStyle(el).color` etc.) rather than trusting what the CSS
*looks* like it should resolve to — several bugs in this project only
became obvious that way.

`body`/`html` backgrounds are a separate trap: they're **ancestors** of
`.app-shell`, so no `[data-streamer]` selector can reach them. If a
streamer's outer page gutter (visible on wide viewports, since
`.app-shell` caps at `540px` and centers) needs to differ, you have to
toggle a class on `document.body` from a `useEffect` in `AppFrame.tsx` and
target `body.your-class` in CSS — see `nexplay-halloween-bg` for a working
example.

## Seasonal theme (Halloween) — OFF as of 06/11/2026, flags kept for reuse

What started as an Enjoy-only (`slug: "nexplay"`) reskin was shared by every
streamer in the roster, each fully reversible independently. **All gate
constants are currently `false`** — season ended, reverted back to each
streamer's original look. Code for both looks is still intact (nothing
deleted), so next Halloween just flip the constants back to `true` again,
no re-entering art/copy.

```text
NEXPLAY_HALLOWEEN_MODE, LHAM_HALLOWEEN_MODE, HOLDEN_HALLOWEEN_MODE,
TOP_HALLOWEEN_MODE, KIM_HALLOWEEN_MODE,
IVY_HALLOWEEN_MODE, WILLIAM_HALLOWEEN_MODE, ZEN_HALLOWEEN_MODE,
LILY_HALLOWEEN_MODE, LILIN_HALLOWEEN_MODE,
MIGUEL_HALLOWEEN_MODE, AMMY_HALLOWEEN_MODE, GRACE_HALLOWEEN_MODE
```

**Nutt and Irada were removed from the roster entirely on 06/11/2026**
(both left) — not just reverted. Their `*_HALLOWEEN_MODE` constants,
`*_STREAMER` configs, links, hero slides, routes, GA4 measurement ID
entries, and ad-rotator subdomain entries are all gone, not merely
disabled. If either name comes up in old context, they're no longer part
of this codebase.

Flipping any one of these to `false` and redeploying restores that
streamer's original look exactly — images, copy, theme colors, header/nav
style, all of it — because **both versions are kept side by side in the
code**, never overwritten. The pattern per streamer (see any `*_STREAMER`
block in `data/streamers.ts` for a concrete example):

```ts
const X_DEFAULT_LOOK = { heroImage, avatarImage, heroAlt, heroTitle, heroHighlight, theme } as const;
const X_HALLOWEEN_LOOK = { heroImage: "/streamers/x/hero-halloween.webp", ... } as const;
const xLook = X_HALLOWEEN_MODE ? X_HALLOWEEN_LOOK : X_DEFAULT_LOOK;
// X_STREAMER then reads every seasonal field from `xLook`, not hardcoded.
```

- **Gate function**: `usesEnjoyHalloweenUi(streamerSlug)` in
  `data/streamers.ts` is the single source of truth for "is this streamer
  in Halloween mode right now" — it just OR's together all the `*_MODE`
  constants. Every component (`AppFrame.tsx`, `BottomNavigation.tsx`,
  `CTAButtons.tsx`, `HeroBanner.tsx`, `PromotionCarousel.tsx`,
  `SocialSection.tsx`, `data/promotions.ts`) calls this function — **never
  hardcode a streamer-slug check for Halloween UI**, always go through it,
  so adding a new streamer to the theme only touches one function.
- **Shared UI, per-streamer art**: every Halloween streamer uses Enjoy's
  own button/nav/social-card textures and promo-card art (identical
  assets, same URLs under `/streamers/nexplay/...` and
  `/promotions/...`) — only each streamer's own hero photo
  (`public/streamers/<slug>/hero-halloween.webp`) and page-background
  image (`public/streamers/<slug>/halloween-bg.webp`) differ. Several
  streamers intentionally **reuse another streamer's background file**
  (e.g. William reuses Top's, Ivy and Miguel reuse Kim's, Lily and Lilin
  share one scene between them; Zen and Ammy reuse Nutt's — that image
  file is still on disk under `/streamers/nutt/` even though Nutt is no
  longer in the roster) rather than getting a unique scene — check
  `app/globals.css` for that streamer's
  `.app-shell[data-streamer="X"][data-seasonal="halloween"]` rule to see
  which image it actually points at before assuming it has its own.
- **`scripts/sync-streamer-enjoy-ui.mjs`** (runs automatically via
  `predev`/`prebuild`) is what makes "shared UI" work without copy-pasting
  ~140 CSS rules by hand: it parses `app/globals.css` with PostCSS, finds
  every rule scoped to Enjoy's Halloween selector
  (`.app-shell[data-streamer="nexplay"][data-seasonal="halloween"]`,
  excluding the page-background rule itself, which every streamer needs
  its own version of), clones it for each streamer in its
  `sharedStreamers` array with the selector swapped, and writes the
  result to the **generated, git-tracked**
  `app/streamer-enjoy-ui.generated.css` (imported in `app/layout.tsx`).
  **Do not hand-edit that generated file** — edit Enjoy's own rules in
  `app/globals.css` and the generator picks up the change on next
  `npm run dev` / `npm run build`. To add a new streamer to the shared
  theme: add its slug to `sharedStreamers` in the script, add its own
  `body.<slug>-halloween-bg` + page-background rule by hand in
  `app/globals.css` (copy an existing streamer's block, point the `url()`
  at that streamer's own or reused background image), then re-run the
  script (or just `npm run dev`/`build`, which runs it automatically).
- Every Halloween-only CSS rule is scoped to
  `.app-shell[data-streamer="<slug>"][data-seasonal="halloween"]` — the
  `data-seasonal` attribute is set from `usesEnjoyHalloweenUi(streamer.slug)`
  in `AppFrame.tsx`. **Never style a Halloween look with a plain
  `[data-streamer="<slug>"]` selector** — it won't revert when the mode
  flips off, and you'd have to hunt it down by hand later.
- `body.<slug>-halloween-bg` classes (toggled in `AppFrame.tsx`'s
  `useEffect`) handle the page-gutter background on wide viewports — see
  the CSS trap note above for why this can't be a `[data-streamer]`
  selector.
- Register/LINE button colors (yellow `#FFCC00` blink / lime `#99FF00`
  blink) are a **separate, permanent** Enjoy-only feature, not part of the
  Halloween theme — don't gate those behind `data-seasonal`.

**Any streamer not in the list above must stay completely unaffected.**
The standard verification step after any Halloween-theme change is: open
a streamer that wasn't touched (e.g. `/lily` when you changed `/kim`) and
confirm it looks identical to before.

## Analytics & tracking — already implemented, don't re-add

- **GA4**: `lib/analytics.ts`, per-streamer Measurement IDs via
  `NEXT_PUBLIC_GA4_MEASUREMENT_ID_<SLUG>`, consent default granted.
- **Meta Pixel + Conversions API**: `lib/metaPixel.ts`,
  `components/MetaPixel.tsx`, `app/api/meta-capi/route.ts`. Pixel ID is
  shared across all streamers (`NEXT_PUBLIC_META_PIXEL_ID`); the CAPI
  access token is a Cloudflare secret (`wrangler secret put
  META_CAPI_ACCESS_TOKEN`), read via `getCloudflareContext()` —
  **`process.env` does not work for secrets, only for `NEXT_PUBLIC_*`
  values.**
- Custom event tracking (`trackEvent` in `lib/analytics.ts`) already
  covers register/line/hero-cta/promotion/social/bottom-nav clicks.
- **Independent click counter**, per streamer — built because Meta Ads
  Manager's own click numbers don't match reality for livestream ad
  traffic, and because GA4 isn't configured for every streamer yet.
  `trackLinkClick(streamerSlug, "visit" | "register" | "line")` in
  `lib/analytics.ts` writes one row per call; nothing is inferred from GA4
  event names, which don't all carry the same shape. Three link types,
  **not summed together** — `register`/`line` are a subset of visitors
  taking an on-page action, not additional arrivals on top of `visit`:
  - `"visit"` — one per browser session (not per route change), fired
    from `AppFrame.tsx` on first mount via a `useRef` guard. This is the
    number comparable to Meta Ads Manager's "Link Clicks" metric — an
    arrival from the ad link, regardless of what the visitor does next.
  - `"register"` / `"line"` — called explicitly at every surface that
    opens a streamer's register or LINE link — `CTAButtons.tsx`,
    `LineOnlyCTA.tsx`, `HeroBanner.tsx`'s slide CTA,
    `PromotionCarousel.tsx` / `SecondaryExperiences.tsx`'s promo-card CTA,
    `BottomNavigation.tsx`'s external nav item, `SocialSection.tsx`'s LINE
    card, the `/follow` page's LINE button, and `AppFrame.tsx`'s
    search-panel quick links. **Any new register/LINE link surface must
    call `trackLinkClick` too — and, per request, also fire a canonical
    `trackEvent("register_click" | "line_click", { streamer_slug,
    placement })` (GA4) and `trackMetaEvent("Lead" | "Contact",
    { content_name, streamer_slug })` (Meta Pixel) alongside it**, even if
    that surface already fires its own more specific event
    (`hero_cta_click`, `promotion_click`, `bottom_navigation_click`,
    `social_follow_click`, etc.) — the specific event stays for UI-level
    analysis, the canonical one is what makes "total register/LINE
    clicks" comparable across every entry point, in GA4 and Meta Ads
    Manager alike. A new page that should count as a landing surface
    (i.e. gets its own `visit` row) needs nothing extra — `AppFrame.tsx`
    already wraps every route.
  - Writes to Cloudflare D1 (`LINK_CLICKS_DB` binding, database
    `nexplay-link-clicks`) via the public, unauthenticated
    `app/api/track-click/route.ts` (called directly from visitors'
    browsers — validates `streamer_slug`/`link_type` against known values,
    nothing else).
  - Reads via the authenticated `app/api/click-report/route.ts`
    (`x-api-key` header checked against the `CLICK_REPORT_API_KEY`
    secret — `.dev.vars` locally, `wrangler secret put
    CLICK_REPORT_API_KEY` in production) — meant for a server-to-server
    caller (e.g. a droplet-side script building an end-of-live report),
    not the browser. Takes optional `from`/`to` ISO query params (UTC,
    defaults to the last 24h) and returns, per streamer, `{visit,
    register, line}` as three separate counts (no combined "total" field
    — don't reintroduce one, it was ambiguous: register+line can over- or
    under-count visit depending on how many buttons one visitor clicks).
  - Schema: `migrations/0001_create_link_clicks.sql` +
    `migrations/0002_add_visit_link_type.sql` (widens the `link_type`
    CHECK constraint — SQLite needs a table rebuild for that, can't
    `ALTER` it in place). One row per click/visit (`streamer_slug`,
    `link_type`, `clicked_at`), not a running counter, so any time window
    (e.g. one specific live session) can be counted after the fact. Apply
    new migrations with `npx wrangler d1 migrations apply
    nexplay-link-clicks --remote` (and `--local` for the dev D1 instance).

## Other things already built (don't rebuild from scratch)

- **In-app-browser gate** (`components/InAppBrowserBanner.tsx`): a
  mandatory full-screen blocker for visitors inside Facebook/Instagram's
  in-app WebView, because that WebView blocks `line://` scheme launches.
  Shown on every page via `app/layout.tsx`.
- **Ad rotators** (`go.` / `friend.` subdomains in `middleware.ts`):
  randomly fan out to one of the 13 streamer subdomains, used for Meta ad
  campaigns. `friend.` exists specifically to separate Ads-driven LINE
  friend-adds from organic ones in LINE's own Friend-paths analytics.
- **Bonus claim system** is currently **hidden from the UI** on every
  streamer (removed from `HomeExperience.tsx` on request) but the
  underlying components/API (`ClaimBonusEntry.tsx`, `ClaimBonusSheet.tsx`,
  claim API routes) are still intact, not deleted. Don't assume it needs
  building — ask before touching it, since it's wired to a real backend
  (Google Sheets + a droplet service) outside this repo.

## Workflow expected on every change

1. Read the current implementation before editing — don't guess.
2. `npx tsc --noEmit -p .` then `npm run build` before every deploy.
3. Visually verify in a real browser at both a mobile width (~375px) and a
   wide desktop width (~1400px) — several bugs in this project only
   showed up at one specific width.
4. If the change targets one streamer, **open at least one other
   streamer's page and confirm nothing changed there.**
5. Check browser console for errors/warnings (React key collisions,
   missing images, etc.) — don't rely on visual inspection alone.
6. Deploy, then re-verify on the real production URL in a **fresh tab**
   (see the ChunkLoadError gotcha above).
7. Report exactly what changed and what was verified — don't claim
   something works without having actually looked at it rendered.
